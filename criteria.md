## 1. False positives on human writing

**Target:** In each evaluation trial, no more than 1 out of exactly 10 human-written submissions should receive the `ai` label. The `ai` label is the label set by the thresholds in `config.py` (currently `AI_THRESHOLD = 0.69`).

The human-written evaluation set will consist of exactly 10 samples of my own writing, written before the evaluation trials begin. The exact same samples will be used in every trial without modification. Each sample must contain at least 100 words. The set will not include any calibration samples, including the geology, *Rich Dad/Poor Dad*, or other calibration samples.

**Why this matters:** Using pre-existing, personally written samples creates a fixed baseline that cannot be adjusted to fit evaluation results. Reusing the same samples across trials makes the results comparable and helps measure whether the system incorrectly flags genuine human writing. I allow at most one false positive rather than requiring zero because a detector may make occasional mistakes, but a wrong accusation against a writer is more costly than missing some AI-generated text.

## 2. Score separation

**Target:** In each evaluation trial:

- The combined score is the value returned by `scoring.combine_signals` (currently an equal-weight average of the model and style scores).
- The average combined score for AI-generated samples must be at least 0.15 higher than the average combined score for human-written samples. This is a starting target for average group separation, not a claim of per-sample accuracy.
- At least 7 out of exactly 10 AI-generated samples must receive a combined score higher than the average combined score of the human-written samples.

The AI-generated evaluation set will consist of exactly 10 samples generated by an AI writing tool before the evaluation trials begin. Each sample must contain at least 100 words. The exact same samples will be used in every trial without modification. Neither evaluation set will include any calibration samples, including the geology, *Rich Dad/Poor Dad*, or other calibration samples.

**Why this matters:** A 0.15 average gap is a measurable initial separation target, while acknowledging that the scores are heuristic and may overlap. Requiring at least 70% of AI samples to exceed the human-set average checks that separation is reasonably consistent and is not driven only by a few unusually high-scoring samples, while allowing some individual misses.

## 3. Label coverage

**Target:** Each evaluation trial, using the combined human-written and AI-generated evaluation sets, should produce all three possible labels at least once: `human`, `unsure`, and `ai`.

**Why this matters:** The system should not classify every submission as AI or human. The unsure category is important because the signals may disagree or produce a score that does not justify a confident decision. This criterion checks that each label is reachable, not that the labels are accurate.

## 4. Appeal workflow

**Target:** For a manually tested appeal, a valid appeal is a JSON object with an existing `content_id` that has an original decision and a non-empty string `reasoning` value after whitespace is stripped. The appeal should receive a successful response, create an appended audit-log entry with status `under_review`, and preserve the original decision in the audit history. The `/appeal` route enforces these validity requirements.

**How I verify it:** I verify appeals manually because the evaluation runner does not test them:

1. Submit a valid piece of text and save its `content_id`.
2. Submit an appeal with that ID and non-empty reasoning.
3. Check that the response is HTTP 200 and reports status `under_review`.
4. Inspect the audit history to confirm an `under_review` appeal entry was appended and the original decision remains unchanged.

**Why this matters:** Writers should have a way to challenge a decision. An appeal should create a review record rather than silently changing the original score or automatically rerunning the detector.

## 5. Invalid submission handling

**Target:** Every invalid /submit request must receive a 4xx response, produce no normal classification, and create a rejection audit-log entry rather than a normal decision entry. This includes malformed JSON, non-object JSON, missing or invalid text, missing or invalid creator_id, and text containing fewer than three GPT-2 tokens. Very long otherwise-valid text is outside this criterion.

**Why this matters:** Invalid requests should be rejected clearly rather than causing unexpected errors or creating misleading classification records. Checking the audit log ensures that invalid input does not leave behind a misleading decision record.
